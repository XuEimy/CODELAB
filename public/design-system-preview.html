面向任何游戏的设计系统

真正该做的不是“蛇身 / 樱桃炸弹”的表单，而是一个可换游戏的通用参数框架

同一个设计工具以后要服务贪吃蛇、植物塔防、平台跳跃、卡牌战斗，甚至聊天式玩法。所以第一层必须是 通用参数框架，第二层才是每个游戏自己的 游戏 schema，第三层再叠加 vibe 语义层，把“春日、危险、软萌、机械”这种抽象词映射成成组参数。

三层结构一眼看懂
1. 通用参数框架 先定义所有游戏都通用的对象与能力类别，比如 场景 / 角色 Actor / 能力 Ability / 资源 / 规则 / 表现。
2. 游戏 schema 每个游戏只提供自己的对象目录和参数字典。换游戏时换 schema，不需要重写整个 UI。
3. vibe 语义层 把抽象氛围词映射成参数组合，让“危险感”“春日感”“软萌感”变成可落地的调参。

通用参数框架

底层骨架

这一层不绑定具体游戏，而是先定义“任何游戏都会有的对象类别”。设计工具 UI 只负责把这些类别渲染成目录和检查器。

Universal Parameter Framework
以后换游戏也不重做 UI

画布、地图、镜头、昼夜、天气、背景层

角色 Actor

玩家、敌人、NPC、召唤物、伙伴

能力 Ability

攻击范围、冷却、能量、伤害、弹道、触发条件

资源 Resource

血量、金币、阳光、经验、魔法、体力

规则 Rules

胜负条件、刷新节奏、碰撞、升级、生成逻辑

表现 Feedback

游戏 schema

每个游戏自定义

通用框架只提供槽位，真正让 UI “知道这个游戏有什么东西”的，是每个游戏自己的 schema。比如贪吃蛇和平台跳跃，可以完全不是一套对象，但仍共用同一套设计工具。

vibe 语义层

让“感觉”变成参数

这层不是替代具体参数，而是站在参数之上。用户先说“我要更危险、更春日、更软萌”，系统再把这些语义映射成一整组数值变化。

Vibe Semantic Layer
更适合你说的 vibe design

战斗 vibe

危险 / 爽快 / 紧绷 / 沉稳 / 轻松

软萌 / 凶狠 / 笨拙 / 灵活 / 沉着
“危险樱桃炸弹” 的语义映射 语义 → 参数
春日 更亮、更轻、更多花粉粒子、伤害显示更柔和
危险 更高饱和、更大爆炸半径、更快预警闪烁
机械 硬边、冷色、爆炸音更脆、UI 更规则
软萌 圆角更大、抖动更轻、危险提示更可爱
映射结果
语义输入 樱桃炸弹 = 春日 40% + 危险 60%
自动翻译 攻击范围 +1、爆炸色偏暖、烟雾透明度降低、预警节奏加快
最终落地 仍回写到具体参数目录里，用户可以继续细调，不会变成黑盒。
我的推荐顺序是：先做通用参数框架 + 游戏 schema，先把“任何游戏都能挂进去”的目录系统建起来； 然后第二阶段再做 vibe 语义层，让抽象风格词去批量调参。 这样你以后不管做贪吃蛇、植物塔防、平台跳跃还是别的玩法，这个设计工具都不用推倒重来。
